🎯 Contexte et objectifs

Le problème

Une organisation héberge un site vitrine WordPress et un outil de gestion de parc GLPI. Chaque application repose sur un seul serveur web et une seule base de données : une mise à jour ratée, un disque plein ou un redémarrage, et le service s'arrête.

Client ──► Serveur web ──► Base de données
             (SPOF)            (SPOF)

Les objectifs

  • Supprimer les points uniques de défaillance (SPOF) des couches web et données.
  • Répliquer la base de manière synchrone, sans perte de données.
  • Répartir la charge et écarter automatiquement un serveur en panne.
  • Segmenter le réseau avec un filtrage deny-by-default.
  • Prouver la tolérance aux pannes par des tests reproductibles.
  • Documenter pour qu'un tiers puisse reconstruire le lab.

⚙️ Fonctionnement de la haute disponibilité

🌐

Couche web

WEB-01 et WEB-02 servent le même site. HAProxy teste chaque serveur toutes les 2 s : après 3 échecs, il est retiré (mesuré : 9 s, 6 requêtes sur 6 servies par l'autre serveur) ; après 2 succès, il est réintégré.

🗄️

Couche données

Galera réplique chaque transaction avant de la valider : aucune donnée confirmée n'est perdue. Le cluster reste actif tant qu'il a la majorité (2 nœuds sur 3) : c'est le quorum, qui empêche deux moitiés de diverger (split-brain).

🔀

Point d'entrée unique

Applications et clients ne connaissent que 10.0.10.2. WordPress et GLPI se connectent à la base via 10.0.10.2:3306. Les requêtes vont à MYSQL-01, les deux autres nœuds restent en secours (pas de conflit d'écriture) : si MYSQL-01 tombe, HAProxy bascule sans toucher aux applications.

💡 Haute disponibilité ≠ sauvegarde. Un DROP TABLE accidentel est répliqué instantanément sur les 3 nœuds : seule une sauvegarde permet de revenir en arrière.

📡 Supervision et journaux

La haute disponibilité cache les pannes : un cluster peut tourner sur 2 nœuds sans que personne ne le voie. La VM ZABBIX (10.0.30.3, zone d'administration) surveille donc les 12 VM et réunit leurs journaux, sans VM ni adresse supplémentaire : trois services, chacun sur son port.

📊

Zabbix 7.0 LTS

12 hôtes supervisés : agent sur les 8 VM Linux, ping pour pfSense et l'annuaire. Interface publiée sur :2231. Prochaine étape : les alertes.

📥

Rsyslog central

Les 8 VM Linux envoient automatiquement une copie de leurs journaux en TCP 514. pfSense n'ouvre ce port qu'aux serveurs prévus, et jamais sur le WAN.

🔎

LogAnalyzer

Lecture des journaux de toutes les machines au même endroit. Accès par :2233, avec un compte et depuis un réseau d'administration seulement.

⚠️ Limites assumées : LogAnalyzer est en HTTP avec authentification Basic (accès de laboratoire, à chiffrer par VPN ou HTTPS) ; les journaux de pfSense et des postes Windows ne sont pas encore collectés ; supervision et journaux partagent la même VM.

🛠️ Incidents rencontrés et résolus

Cluster Galera « non-Primary »

Cause : perte du quorum après l'arrêt brutal de plusieurs nœuds.
Solution : analyse de grastate.dat et galera_recovery, bootstrap du nœud le plus à jour uniquement.

« Connection refused » sur 3306

Cause : bind-address = 127.0.0.1 par défaut : MariaDB n'écoutait qu'en local.
Solution : chaque nœud écoute sur sa propre IP (10.0.20.1, .2, .3).

« dpkg was interrupted »

Cause : installation coupée en cours de route.
Solution : dpkg --configure -a puis apt --fix-broken install ; installations longues dans tmux.

« rsync: command not found »

Cause : paquet absent sur une Debian minimale, alors que Galera (SST) et la synchro WordPress en ont besoin.
Solution : installation sur tous les nœuds concernés.

GLPI : erreur 404

Cause : règles de réécriture Apache mal placées, DocumentRoot hors de public/.
Solution : mod_rewrite activé, règles dans le bloc <Directory> du dossier public/.

SSH « Permission denied (publickey) »

Cause : clé privée placée dans authorized_keys, qui ne doit contenir que des clés publiques.
Solution : ssh-copy-id avec la clé publique, nouvelle paire de clés.

« REMOTE HOST IDENTIFICATION HAS CHANGED »

Cause : VM réinstallée, donc nouvelle clé d'hôte.
Solution : empreinte vérifiée depuis la console Proxmox avant ssh-keygen -R (c'est aussi le symptôme d'une attaque).

Conflit avec le compte « haproxy »

Cause : utilisateur humain nommé haproxy, comme le compte système du service.
Solution : compte d'administration haproxyadmin, compte système laissé au paquet.

LogAnalyzer : « 403 Forbidden »

Cause : Apache n'autorisait que la zone d'administration ; le NAT de pfSense garde l'adresse du poste, qui était donc refusée (AH01630).
Solution : réseau du poste ajouté à Require ip, en gardant l'authentification obligatoire (Require valid-user).

Journaux : rien n'arrive du serveur web

Cause : le fichier de transfert 90-centralisation.conf existait, mais le paquet Rsyslog n'était pas installé sur la Debian.
Solution : apt install rsyslog, service activé, puis test logger : 8 VM sur 8 reçues.

⚠️ Limites et améliorations

Ce qui reste à améliorer

  • HAProxy unique → second HAProxy + Keepalived (IP virtuelle partagée).
  • pfSense unique → deux pare-feu en CARP.
  • Health-check SQL → vérifier l'état Galera (Synced), pas seulement que MariaDB répond.
  • Fichiers WordPress → synchronisation planifiée ou stockage partagé (NFS, GlusterFS) : pas encore en place.
  • HTTPS, alertes Zabbix, sauvegardes automatisées.
  • Journaux : les 8 serveurs Linux sont centralisés (Rsyslog + LogAnalyzer) ; restent pfSense, les postes Windows et un accès chiffré.
  • Un seul hôte Proxmox : la redondance est logique, pas physique.
